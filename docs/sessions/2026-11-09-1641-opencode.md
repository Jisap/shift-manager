## Seguimiento (17:16) — rendimiento del calendario anual

Se añadió `src/lib/engine/calendar.perf.test.ts`, un test de rendimiento **opt-in** (entorno `node`, se salta sin `PERF=1`, por lo que no ralentiza `npm run test`). Cada escenario se calienta 5 veces y se ejecuta durante ~750 ms; se reportan mínimo, mediana, p95, media y ops/s.

Comando:

```powershell
$env:PERF=1; npx vitest run src/lib/engine/calendar.perf.test.ts --reporter=verbose --silent=false
```

Resultados en un equipo de desarrollo (365 días, `Europe/Madrid`):

| Escenario                                             | Mediana |     p95 |   Media |   Throughput |
| ----------------------------------------------------- | ------: | ------: | ------: | -----------: |
| `resolveRange` · semanal + 1 turno                    | 32,3 ms | 37,3 ms | 33,1 ms |   30,2 ops/s |
| `resolveRange` · rotativo + nocturno + 30 excepciones | 25,1 ms | 28,8 ms | 25,3 ms |   39,5 ops/s |
| `resolveRange` · 50 patrones históricos (peor caso)   | 35,7 ms | 36,8 ms | 35,5 ms |   28,1 ops/s |
| `buildStatistics` · año completo                      | 0,12 ms | 0,14 ms | 0,12 ms | ~8.150 ops/s |
| Estadísticas completas + buckets mensuales            | 0,14 ms | 0,15 ms | 0,14 ms | ~6.920 ops/s |

Conclusiones:

- El motor resuelve un año completo en **~25–36 ms** de CPU, muy por debajo del límite práctico de una query de Convex y de un frame de UI. El peor caso (50 patrones) solo añade ~3 ms.
- Las agregaciones del dashboard son despreciables (< 0,2 ms); el coste está en resolver los días.
- El cuello de botella es la conversión de hora local a instante (`TZDate` + `Intl`), con ~2 conversiones por día. Habría margen para optimizar con caché de offsets, pero **no es necesario para el MVP**; se deja anotado como mejora futura.
- No se modificó el motor ni el esquema.

Verificación tras el cambio: `typecheck`, `lint`, **150 tests unitarios + 1 test de rendimiento omitido** (18 archivos) y benchmark ejecutado con `PERF=1` correctamente.
